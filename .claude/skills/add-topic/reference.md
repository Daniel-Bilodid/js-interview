# Еталон теми

Читається один раз за сесію. Далі пиши за цим зразком, а не за загальним уявленням про «хорошу статтю».

> Приклади нижче взяті з уже наявних тем — вони проходять валідатор. Це зразки **тону й щільності**, а не заготовки для копіювання.

## Скелет

```ts
  {
    id: 'rn-metro',
    title: 'Що таке Metro і чим він відрізняється від webpack?',
    definition:
      '<2-5 речень. Суть → механізм → наслідок. Це те, що людина скаже вголос інтервʼюеру.>',
    why: '<1-4 речення. Яку проблему це вирішує. Вхід у тему для того, хто бачить її вперше.>',
    simple:
      '<6-14 речень. Механізм простими словами. Не переказ визначення іншими словами.>',
    related: [
      {
        title: '<коротка назва суміжного поняття>',
        text: '<120-550 символів: що це і чому без нього основна тема не розкривається>',
      },
      // ще 1-3 таких
    ],
    codeExamples: [
      {
        label: '<що саме показує приклад>',
        code: `// 3-45 рядків, коментарі українською`,
      },
    ],
    seniorNotes: [
      '<4-6 пунктів по 80-400 символів. Конкретні факти, а не поради.>',
    ],
  },
```

## Поле за полем

### `title`

Так, як питання ставить інтервʼюер, а не як називається розділ документації.

- ✅ `'Як працює віртуалізація у FlatList і як оптимізувати довгий список?'`
- ✅ `'Застосунок гальмує. Як ти шукатимеш причину?'`
- ❌ `'FlatList'` — це назва теми, а не питання
- ❌ `'Оптимізація списків у React Native'` — заголовок статті

### `definition`

Найважливіше поле: воно єдине показується у всіх трьох режимах глибини, включно з «Повторенням» перед співбесідою. Пиши так, щоб це можна було сказати вголос за 40-60 секунд і зупинитись.

Структура: **суть одним реченням → механізм → наслідок або межа застосування.**

✅ Так (з теми `rn-what-is`):

> React Native — це фреймворк, у якому логіку застосунку ти пишеш на JavaScript і React, а інтерфейс малюють справжні нативні компоненти платформи: UIView на iOS і android.view.View на Android. Тобто React виступає не бібліотекою для DOM, а описом дерева, яке рендериться нативними віджетами. Це принципово відрізняє його від Cordova чи Capacitor, де застосунок — це вебсторінка всередині WebView, і від Flutter, який не бере нативні компоненти взагалі, а сам малює кожен піксель на канві.

Чому це працює: перше речення дає повну відповідь; друге уточнює механізм; третє відмежовує від сусідніх технологій — саме туди піде наступне питання інтервʼюера.

❌ Так не треба:

> React Native — це дуже популярний фреймворк для створення мобільних застосунків. Він має багато переваг і широко використовується в індустрії. Давайте розберемось, як він працює.

Три речення, нуль інформації, плюс анонс замість відповіді.

### `why`

Відповідає на «а навіщо це взагалі придумали». Показується лише в режимі «З нуля» — це вхід для людини, яка бачить тему вперше. Пиши про проблему, яка існувала **до** появи цієї штуки.

✅ (з теми `rn-threads`):

> Мобільний інтерфейс має малювати новий кадр кожні 16 мілісекунд, інакше користувач бачить ривки. Якби вся робота йшла в одному потоці, будь-який важкий цикл у JavaScript моментально ламав би прокрутку.

### `simple`

Пояснює **механізм**, а не переказує визначення синонімами. Аналогія доречна тоді, коли вона щось прояснює — і одразу після неї має йти те, що вона пояснює, буквально.

Хороший каркас: аналогія → як це працює насправді → що з цього випливає на практиці → найчастіша помилка.

✅ (з теми `rn-lists`, скорочено):

> Уяви вікно поїзда: ти бачиш лише невеликий шматок краєвиду, хоча дорога довга. FlatList робить те саме — тримає у памʼяті лише те, що близько до екрана, плюс невеликий запас. Коли елемент їде далеко за межі вікна, він розмонтовується, а на його місце ставиться порожній простір потрібної висоти, щоб смуга прокрутки не стрибала. Найважливіше для розуміння оптимізації: список постійно мусить знати, якої висоти кожен елемент…

### `related`

2-4 суміжні поняття, без яких основна тема провисає. Це не «дивись також» — це те, про що інтервʼюер спитає наступним питанням.

Бери те, що справді потрібне для розуміння: сусідній механізм, типове непорозуміння, історичний контекст, платформенна відмінність.

- ✅ `'Чому Text обовʼязковий'`, `'Що змінила нова архітектура'`, `'Одиниці вимірювання'`
- ❌ `'Корисні посилання'`, `'Додаткова інформація'`

### `codeExamples`

1-3 приклади. Перший показує канонічне використання, другий — типові помилки через `// ❌` і `// ✅`. Код має бути самодостатнім і читатись без запуску.

```ts
{
  label: 'Чотири помилки, що вбивають віртуалізацію',
  code: `// ❌ нова функція на кожному рендері — memo не спрацює ніколи
<FlatList renderItem={({ item }) => <Row item={item} />} />

// ❌ FlatList усередині ScrollView — віртуалізація вимикається
<ScrollView>
  <FlatList data={data} />   {/* висота нескінченна → рендериться ВСЕ */}
</ScrollView>`,
}
```

Рядок обгорнутий у backtick-и, тому всередині екрануй `` \` `` і `\${`.

### `seniorNotes`

Найцінніше поле — саме воно відрізняє довідник від переказу документації. **Факти, а не поради.** Кожен пункт має містити щось перевірюване: назву API, число, версію, назву типової помилки, конкретний компроміс.

✅ Так:

> `getItemLayout` працює тільки при однаковій висоті елементів. Для змінної висоти правильна відповідь — не вигадувати обхідні шляхи, а брати FlashList із estimatedItemSize.

> Синхронні виклики через JSI можливі, але блокують JS-потік. Синхронність виправдана лише для миттєвих читань на кшталт константи, і ніколи — для роботи з диском чи мережею.

> Hermes є типовим рушієм починаючи з React Native 0.70, тому фраза «його треба вмикати вручну» видає незнайомство з сучасними версіями.

❌ Так ні:

> Треба стежити за продуктивністю застосунку. — порада без змісту
> FlatList — потужний компонент з багатьма можливостями. — реклама
> Використовуйте мемоізацію для оптимізації. — не нюанс, а загальне місце

Корисний тест: якщо пункт можна дослівно перенести в тему про іншу технологію — він порожній, переписуй.

## Технічні обмеження

- Українською. Апостроф лише `ʼ` (U+02BC). Ніколи `'` (зламає рядок) і не `’`.
- `definition`, `why`, `simple`, тексти `related` — **одним рядком без `\n`**. Абзаци робить `toParagraphs()`.
- Без markdown у прозі: ні `**`, ні списків, ні backtick-ів. Підсвітку коду в тексті робить `RichText` за словником.
- Якщо тема вводить нові терміни (назви API, класів, рушіїв), додай їх у `KEYWORDS` у `js-interview/src/components/RichText.tsx` — інакше вони не підсвітяться.
- Заборонені штампи: «дуже важливо», «варто зазначити», «слід зауважити», «як відомо», «у сучасному світі», «не секрет», «це дуже потужний», «простими словами кажучи».

## Чек-лист перед перевіркою

1. `id` унікальний серед **усіх** файлів даних, не `practice`
2. `title` — питання, 20-150 символів
3. `definition` можна сказати вголос і зупинитись — без анонсів
4. `why` про проблему, що існувала до появи технології
5. `simple` пояснює механізм, а не повторює `definition`
6. `related` — те, що спитають наступним питанням
7. кожен `seniorNote` містить конкретику й не підходить іншій технології
8. `id` вставлений у `*_ORDER` на місце за складністю
9. `npm run check:topics -- <id>` та `npx tsc -b` проходять
